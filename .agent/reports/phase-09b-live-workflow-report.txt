3. RUNTIME COST OF THE NEW LAYER
----------------------------------

Measured on the 59.25 s of program video this delivery contains:

    motion envelope decode, 64x36 @ 10/s   3.52 s      (Phase 9a, unchanged)
    spatial grid decode,    32x18 @ 10/s   3.52 s      (Phase 9b, new)
    spatial statistics over 592 samples    0.11 s      (pure Python, no numpy)

So the whole spatial layer costs **~3.6 s per minute of timeline**, about 6% of realtime, and
0.1 s of that is the domain code. It scales linearly and needs no GPU. For reference the
Resolve renders it depends on cost 22 s for the same minute — the analysis is not the
expensive part, the rendering is.

Judged against what it buys (7/15 versus a no-signal 11/15), the correct engineering verdict
is not "it is too slow" but "it is cheap and it does not work". It stays in `gameplay-study`
as measurement and enters no runtime path.

`gameplay-study` takes about a minute and a half. Run it without a short command timeout, for
the same reason as `apply-preview`: the safety model is transactional against *failures*, not
against the process being killed. A kill mid-run leaves a `DAZ_AUDIO_SCRATCH_*` timeline and
possibly a temporary render preset, both disposable by name, because the thing that would
clean them up is the thing that got killed.
