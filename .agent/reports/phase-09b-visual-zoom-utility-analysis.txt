Source `DAZ_INPUT` [216000, 219555) @ 60 fps. Reference `DAZ_OUTPUT_MVP3`, V3, 42 items.

**Every conclusion below is tagged with where it came from**:

**Read sections 1, 2 and 8 before anything else.** Phase 9b was asked whether "would the zoom
add value here" can be represented by generic visual features. The answer on this material is
**no**, and the reason is now specific rather than vague: the zoom is a centred 1.25x push-in
that privileges no screen region, and frame differencing in a first-person game measures the
player's mouse, not the game's events.

No media of any kind was committed. The contact sheets, extracted frames and rendered video
used for section 4 were local, temporary and deleted; this repository is public.


1. WHAT THE GAMEPLAY ZOOM ACTUALLY IS — MEASURED, NOT ASSUMED
---------------------------------------------------------------

[measured] One instance of each of the eleven roles that exist in `DAZ_OUTPUT_MVP3` was
exported with `TimelineItem.ExportFusionComp` and parsed. Every one of them is the same
five-node graph — `Loader -> Transform -> Saver`, with the `Transform`'s `Size` on a
`BezierSpline` and its `Center` on a `PolyPath` — and **there is no Crop, no Mask, no Merge
and no second Transform anywhere**. The whole state model is two numbers.

    state       Transform Size    Centre offset (Fusion, y up)
    X0                 1.00       (0.00, 0.00)
    GAMEPLAY           1.25       (0.00, 0.00)
    FACE_X1            1.50       (0.25, 0.25)
    FACE_X2            2.00       (0.50, 0.50)
    FACE_X3            2.50       (0.75, 0.75)

    role              Size 0 -> 15      Centre path 0 -> 15
    X0_TO_GAMEPLAY    1.00 -> 1.25      (0,0) held
    X1_TO_GAMEPLAY    1.50 -> 1.25      (0.25,0.25) -> (0,0)
    X2_TO_GAMEPLAY    2.00 -> 1.25      (0.50,0.50) -> (0,0)
    GAMEPLAY_TO_X0    1.25 -> 1.00      (0,0) held
    GAMEPLAY_TO_X1    1.25 -> 1.50      (0,0) -> (0.25,0.25)
    FACE_X1/2/3       1.00/1.50/2.00 -> 1.50/2.00/2.50, centre walked one step out
    X1/X2/X3_TO_X0    1.50/2.00/2.50 -> 1.00, centre walked back to (0,0)

**All four transitions into GAMEPLAY converge on exactly the same final state**, and both
transitions out of it start from exactly that state. Every keyframe pair is `[0]` and `[15]`.

`X3_TO_GAMEPLAY` still has no manual instance, so its comp could not be exported — but
[user] the creator has now **confirmed explicitly that it animates fully in 15 frames**, and
[measured] the other eleven roles are unanimous that the endpoint it must reach is
`Size 1.25, centre (0,0)`. The value is no longer marked unconfirmed anywhere (D062).

### The GameplayTargetROI, derived

A Fusion `Transform` maps output `u` to source `(u - C)/size + 0.5`, with `C = 0.5 + offset`.
For `Size 1.25, offset 0` that is `[0.1, 0.9]` on both axes:

    GameplayTargetROI = x [0.10, 0.90], y [0.10, 0.90]   — the central 80%, area 0.64

This is derived in `domain/visual_episodes.Roi.from_transform` from the two measured numbers,
not typed in, and the derivation is checked against the facecam ladder in
`tests/test_visual_episodes.py`: `FACE_X1` comes out as `[0, 0.667]`, `FACE_X2` as `[0, 0.5]`,
`FACE_X3` as `[0, 0.4]` — a nested family of rectangles all anchored in one corner, and
[seen] that corner is exactly where the facecam inset sits in the delivered picture. A ladder
that lands on the facecam by construction is strong evidence the arithmetic is right.

### The consequence, and it is the phase's first real result

**The GAMEPLAY zoom is not a spotlight.** It privileges no region: it is symmetric, centred,
and only 1.25x. What it does is crop the outer 10% of the frame and enlarge the rest by a
quarter. [seen] The outer 10% of this delivery is where the HUD lives — the weapon wheel
along the top, the ammo counter bottom-right, the title card top-left, the kill feed top-right
— so the move trades away UI margin for a slightly bigger middle.

Therefore the phase brief's central hypothesis — *"the zoom is useful when a localized event
falls inside the region the zoom favours"* — is **structurally weak on this material before
any window is measured**: there is no favoured region, and a 1.25x magnification cannot make a
small distant object readable. Section 5 measures it anyway, and the measurement agrees.

### The ROI feature is inert, and the geometry said it would be

`ratio` — activity inside the zoom's region against the whole frame — spans **0.84 to 1.23
over all fifteen windows**, with the negatives (0.92, 1.03, 1.01, 0.92, 1.13) sitting inside
the positives' range. It could hardly do anything else: the ROI is 64% of a centred frame, so
"inside" and "outside" sample the same picture. Inside-vs-outside is a real question for the
*facecam* states, whose ROI is a corner; for GAMEPLAY it is arithmetic noise.

### The negatives have positive twins, and that is the strongest statement of the result

Z-scoring all nine features and finding each window's nearest neighbour **of the opposite
class**:

    gap  8 (GAMEPLAY) <-> gap 11 (X0)   distance 0.92
    gap 10 (X0)       <-> gap  8        distance 1.09
    gap  5 (GAMEPLAY) <-> gap 10 (X0)   distance 1.19
    gap  7 (GAMEPLAY) <-> gap 10 (X0)   distance 1.20
    gap 12 (X0)       <-> gap  7        distance 1.69
    gap  0 (GAMEPLAY) <-> gap  1 (X0)   distance 1.76
    gap 13 (GAMEPLAY) <-> gap 14 (X0)   distance 1.87

Every hard negative has a manual-gameplay window within ~1 standard deviation of it in the
full nine-dimensional feature space. This is not "no threshold was found"; it is **the two
classes containing near-identical pairs**. No classifier over these features, of any shape,
can separate them, and reporting a tuned 12/15 on this data would be reporting an accident.

### Why the features fail, specifically

[measured + seen] Gaps 11 and 12 are visually empty corridors — the player walks and looks
around, nothing happens — and they score `act% 64-66`, `bbox 0.99-1.00`: **the whole frame is
"moving"**. Gap 10, where an NPC really does run at the camera, scores 64.3% — the same. In a
first-person game every mouse movement translates the entire image, and a frame difference
cannot tell that translation from an object crossing the shot.

That is the technical core of the negative result. These features do not measure the game's
events; **they measure the player's camera**. Fixing that needs motion compensation or object
detection, i.e. exactly the dependencies Phase 9b was told not to reach for — and the brief
was right to want the cheap thing tested first, because the cheap thing is now measured to
fail for a nameable reason rather than an unclear one.


6. ZOOM USEFULNESS AS A DECISION, AND THE FOUR HARD NEGATIVES
---------------------------------------------------------------

`domain/visual_episodes.zoom_utility` turns the features into one boolean plus reasons:

    zoom_worthy  =  something happened at all   (peak active cells >= 2%)
                and it is not the whole shot    (mean active cells <= 35%, conc >= 0.30)
                and it is inside the ROI        (ratio >= 1.0)
                and it lasted                   (>= 0.5 s)

[measured] Applied to the 15 windows it fires on gaps 2, 13 and 14 only. Against the human:

    hard negative   verdict   reason given                    is the reason the right one?
    gap  1          X0 ok     event_outside_the_zoom_roi      NO — the real reason is
                                                              "nothing new", and the rule
                                                              reached the right answer by
                                                              measuring the wrong thing
    gap 10          X0 ok     event_covers_the_whole_frame    YES — this is exactly the
                                                              creator's "zoom adds nothing",
                                                              mechanically reproduced
    gap 11          X0 ok     event_covers_the_whole_frame    NO — the screen is empty; the
                                                              "event" is camera pan
    gap 12          X0 ok     event_covers_the_whole_frame    NO — same
    gap 14 (tail)   X0 ok     -- the tail rule, not the visual rule; `zoom_utility` itself
                              calls the near-black outro zoom-worthy

So **all four hard negatives are gated**, and only one of them for the right reason. Meanwhile
eight of the ten positives are gated too (0, 3, 4, 5, 6, 7, 8, 9). The rule is not
discriminating; it is conservative. A rule that says "no" to almost everything gets the
negatives right for free, and the phase brief's own instruction applies: **this is not a
solved rule.**

### What separates "action visible" from "action worth a zoom" — as far as it can be stated

[seen + user] Three properties do appear to distinguish the two, and none of them is currently
measurable from a frame difference:

  * **apparent size of the subject.** gap 9's enemy is a few dozen pixels tall and far away;
    gap 10's NPC is two-thirds of the frame. Same "activity", opposite editorial value.
  * **whether the subject is a subject at all.** gaps 11/12 have no subject, only geometry
    moving because the camera moved.
  * **whether the interesting thing is where the zoom keeps it.** gap 6's creature enters at
    the right edge and gap 11's UI lives along the top — both in the 10% the zoom crops away.

Each of those is a statement about *objects*, and the pipeline has no notion of an object.

8. WHAT PHASE 9b CONCLUDES
----------------------------

1. **The GAMEPLAY zoom's geometry is fully known** [measured]: `Size 1.25`, centre untouched,
   15-frame animation, four entries converging on one state. `GameplayTargetROI` is the
   central 80% of the frame and is derived from those numbers.
2. **The ROI cannot carry the decision**, because a centred 1.25x push-in has no preferred
   region. This was predicted from the geometry and then measured (`ratio` 0.84-1.23 across
   both classes).
3. **Motion topology fails exactly as motion amount did.** Nine spatial features, every class
   range nested, every best threshold 10 or 11 of 15 against a 10/15 baseline, and each hard
   negative has a positive twin within ~1 sigma.
4. **The reason is nameable**: frame differencing in a first-person game measures the camera,
   not the game. Empty corridors score the same "activity" as a charging NPC.
5. **The concept the creator described is real and is about objects** — a subject, its
   apparent size, whether it is where the zoom keeps it. None of that is expressible with
   ffmpeg + numpy frame differences.
6. **A zoom-worthiness gate is nevertheless the right shape for the rule** [user]: secondary
   audio and creator silence can only ever *remove* a candidate, never create one, and that is
   now encoded and tested (D067).
7. **Gap 13 says even a perfect visual reader would not be enough**: the human cut to the game
   over a near-black outro. Some GAMEPLAY decisions are not about what is on screen at all.

**No candidate rule is proposed.** Fabricating one from features whose classes contain twins
would be fitting noise on n=15, and the brief explicitly asked not to. What Phase 9b delivers
instead is a much sharper statement of what the next attempt has to be able to see.


9. WHAT WOULD ACTUALLY MOVE THIS FORWARD
------------------------------------------

In descending order of expected value, none of it implemented here:

1. **A second reference edit that uses gameplay.** Still first, still worth more than
   everything below combined. Fifteen windows from one delivery cannot support a rule, and
   this phase has now failed to find one twice on the same fifteen.
2. **Camera-motion compensation before any spatial statistic.** The cheapest honest version is
   a global translation estimate per sample (a coarse cross-correlation over the 32x18 grid is
   pure numpy and needs no dependency), subtracted before differencing. It would turn "the
   whole frame moved" into "the frame moved 6 cells left, and this one blob did not follow" —
   which is the first measurement in this project that would describe an *object*. It is the
   one classical experiment that is not yet exhausted.
3. **A subject-scale reader.** Only after 2: "how big is the thing that is not the camera" is
   the feature that separates gap 9 from gap 10, and it is the creator's own criterion.
4. If 2 and 3 both fail, a semantic layer is required, and its contract is in section 10.


10. IF A SEMANTIC LAYER IS EVER STUDIED (RESEARCH CONTRACT ONLY)
------------------------------------------------------------------

Not implemented, not a dependency, not called anywhere, and no external service was contacted
during this phase. Recorded only so a future study starts from a precise question:

    input   : N frames of the window, 1920x1080, plus the GameplayTargetROI rectangle
    question: "Is there a subject in this shot — a character, a creature, an object, an
               event — that (a) was not there in the previous seconds, (b) sits inside the
               central 80% of the frame, and (c) is small enough on screen that showing it
               25% larger would materially improve how readable it is?"
    output  : yes/no + which subject + its bounding box + a confidence

The three sub-questions map one-to-one to the three properties section 6 identified and could
not measure. Any such study stays **offline research**: DAZ's runtime must remain ffmpeg +
numpy + Silero, and a rule that cannot be recomputed locally cannot ship (D065).
